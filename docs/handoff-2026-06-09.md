## TL;DR

- The harness (M1–M4) is **done, committed, tested** (26 tests, ruff clean). It ran a full
  **528-run matrix**: `qwen3.5:4b-mlx` vs `gemma4:e4b-mlx` × {passthrough, embedding} ×
  {unconstrained, constrained} × 4 tiers (single/chain/ambiguous/negative), judged by a cloud LLM.
- **Decision so far:** `qwen3.5:4b · passthrough · unconstrained` is shippable for the easy half
  (single 1.0, negative over-call 0.0), decent on chains (0.64), weak on ambiguity/clarify (0.58).
  Gemma over-calls on **55%** of negatives → not shippable as-is. The real gaps are **chains** and
  **clarify-instead-of-guess**.
- **We did NOT test the reasoning-distilled qwen.** That + an updated harness/prompt is the next wave.

## The decision this serves

**Fine-tune a small local model for macOS/MCP tool use, or ship zero-shot with good scaffolding?**
The harness is the instrument. Current read: ship qwen zero-shot for single/negative; chains +
ambiguity need either a better prompt, retrieval/decoding tuning, or a targeted fine-tune. Decide
*after* the next wave (below) closes the cheap gaps first.

## What's built (commands)

```bash
uv venv --python 3.11 && uv pip install -e ".[dev]" && source .venv/bin/activate
tooleval run --model qwen3.5:4b-mlx                 # single cell, passthrough
tooleval matrix --config config/run.example.yaml    # full matrix (writes results/<ts>/)
tooleval report --results results/<ts>              # judge clarify rows + render md/HTML
pytest                                              # 26 tests
```

- Layout: `src/tooleval/{providers,retrieval,tools,eval,report}`, `data/tools/catalog.json`
  (103 tools), `data/tasks/{single,chain,ambiguous,negative}.json` (66 tasks).
- Providers: `ollama.py` (native tool path), `mlx.py` (HF MLX via `mlx_lm`, **lazy import**),
  `litert.py` (Gemma fidelity **scaffold** — `_generate` unimplemented), `openrouter.py` (judge).
- Report → `.claude/artifacts/report-tooleval.html` (gitignored) + `results/<ts>/report.md`.

### Findings
1. **qwen ≫ gemma, on restraint.** qwen over-call = 0.0 everywhere; Gemma = 0.55 (passthrough).
2. **No scaffold wins all tiers.** passthrough+unconstrained best for chains; embedding/constrained
   best for clarify + over-call restraint. Execution-vs-restraint tension.
3. **Best overall cell:** qwen · passthrough · unconstrained (task_pass 0.85).

## Critical caveats (read before trusting numbers)

- ¹ **Constrained decoding breaks multi-step** (chains → 0.0). The Ollama constrained mode
  (`_complete_constrained` in `providers/ollama.py`) emits a *single JSON decision per turn* and
  flattens tool results to text, so it can't sustain iterative calling. **Constrained-cell chain
  numbers are a harness artifact, not model capability.** Fix = native tool-calling + per-tool
  *argument* grammar (Ollama structured-output on args, or llama.cpp GBNF).
- **Embedding recall = 0.68** — naive `nomic-embed-text` with **no task prefixes** dropped the
  gold tool ~32% of the time, mechanically capping embedding single/chain. The **e5 + prefix path
  is already built** (`retrieval/embedding.py`, default now `e5`, prefixes `query:`/`passage:`),
  but this matrix ran on the old naive nomic. Re-run to get true embedding numbers.
- **Small n:** chain=14, ambiguous=12 tasks → each ≈ 7–8%; numbers are noisy.
- **Only the `default` prompt ran.** The prompts axis exists but is untested.

## Environment / gotchas (16GB M2)

- Models are **MLX-in-Ollama tags**: `qwen3.5:4b-mlx`, `gemma4:e4b-mlx` (both tool-call via
  `/api/chat`). `qwen3.5:0.8b` collapses under passthrough (good demo, not representative).
  Exact `qwen3.5:4b`/`gemma4:e4b` registry tags are NOT pulled.
- **`num_ctx=16384`** cap is essential — Gemma allocated KV for its full default window and hit
  17.7GB resident (swap) on 16GB. **`num_predict=2048`** cap — Gemma ran away in `format` mode and
  hung the run. Per-task error resilience + `unload_all` after every run are in place.
- **Judge** = OpenRouter `nvidia/nemotron-3-ultra-550b-a55b:free`, key+model in `.env`
  (`OPENROUTER_API_KEY`, `OPENROUTER_MODEL`; gitignored). Verified discriminating. Verdicts cached
  in `results/cache/`.
- `caffeinate -ims` was used to keep the box awake with the display free to sleep (`pkill caffeinate`
  to stop; it auto-expires on a timeout).

## NEXT WAVE — prioritized plan

**Goal:** close the cheap gaps before deciding on a fine-tune, and answer "does reasoning-distillation
already fix chains/over-calling?"

1. **Test the reasoning-distilled qwen (the headline question).**
   - `uv pip install mlx_lm`; add an `mlx` branch to `config.build_provider` (return `MLXProvider`).
   - Add model cells: `{provider: mlx, model: "mlx-community/Qwen3.5-4B-OptiQ-4bit"}` (clean baseline,
     same base as the Ollama qwen — sanity check) and
     `{provider: mlx, model: "Jackrong/MLX-Qwen3.5-4B-Claude-4.6-Opus-Reasoning-Distilled-v2-8bit"}`.
   - Compare distilled-vs-stock on **chain completion**, **over-call**, **clarify**. If distillation
     already clears the bar → likely **skip the custom fine-tune**.
   - Watch: MLX models are 4–10GB; run sequentially, `unload()` between (16GB). Validate the
     `parse_text_tool_calls` Qwen `<tool_call>` parsing on real output first (smoke 1 task).
2. **e5 embedding re-run.** Pull/serve an e5 model (Ollama GGUF `ollama pull hf.co/...e5...`, or
   `sentence-transformers`), set `retrieval: [{kind: embedding, embed_model: e5, k: 8}]`, re-run.
   Compare recall + chain vs the 0.68 naive-nomic baseline.
3. **Restraint prompt variant.** Add a 2nd entry to `prompts:` and a prompt registry in the runner
   (currently `DEFAULT_SYSTEM_PROMPT` only). Draft: *"Only call a tool when the request clearly needs
   one; answer chit-chat/known-facts directly; if underspecified or an entity is ambiguous/unknown,
   ask a clarifying question instead of guessing; after a tool result, continue any remaining steps
   before replying."* Targets Gemma over-call + both models' over-acting + qwen chain drop-offs.
4. **Fix constrained decoding** (native calling + per-tool arg grammar) so constrained chain numbers
   are real. Until then, footnote them.
5. **Grow hard tiers** to ~30 chain + ~30 ambiguous for tighter estimates.
6. *(lower)* LiteRT-LM provider for Gemma deployment fidelity — implement `litert.py:_generate`.
